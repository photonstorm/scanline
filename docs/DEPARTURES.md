# Where the build departs from the specification

The specification was written from documents and source code, before anything was run. This file lists where the code now differs from it, and why. Each entry should end up as a change to the specification.

## Changed because a spike showed the design was wrong

| The specification says | The code does | Why |
|---|---|---|
| Inject into a worker by evaluating the probe while the worker is held at start, then releasing it. | Hold the worker, set an instrumentation breakpoint for its first statement, release it, evaluate the probe at that pause, then switch the debugger off. | A worker held at start has no WebGPU interfaces yet, so they could not be hooked, and reading `self.location` in it blocks forever. Spike S1. |
| `Target.setAutoAttach` on the page reaches every worker. | Auto-attach is also set on the browser session, and targets are filtered by URL scheme. | Shared and service workers are not children of the page. Browser-level attach also catches the browser's own UI and extension workers, which must be left alone. Spike S1. |
| While the agent owns input, ignore the person's with `Input.setIgnoreInputEvents`, if injected events pass through it. | Not built yet. The probe-side filter is now the plan. | `Input.setIgnoreInputEvents` drops injected events too. Spike S4. |
| Key events send `key`, `code` and the legacy key code. | They send `key`, `code` and `windowsVirtualKeyCode` only, never `nativeVirtualKeyCode`. | With a native key code set, a key event with no text left the next mouse event unacknowledged on macOS. Spike S4. |
| "Wait for the acknowledgements, then release the frame" makes input frame-exact. | The same, for now. | A wheel event is acknowledged before the page receives it, so acknowledgement is not proof of delivery. The host should confirm through the probe's input recorder. Not done yet. Spike S4. |
| The probe replaces `requestAnimationFrame` with a queue. | Each page callback is registered natively, one for one; the gate decides when the native frame fires whether to run or hold it. | Keeps the browser's own ordering and the microtask checkpoint after each callback, which a probe-side queue flushed in one task cannot. |
| Overhead budgets are percentages of CPU frame time (1%, 5%, 15%). | Budgets are absolute costs per graphics call: see "Overhead budgets" below. | On a frame that is nothing but graphics calls, 6–8 ns per call is 16–29%, so a percentage measures the benchmark, not the tool. Decided 10 November 2026 (the owner left the choice to the build). Spike S9. |

## Overhead budgets

Decided 10 November 2026, replacing the percentages in the PRD (section 9.1). They are averages over the calls of a frame, measured by `spikes/s9-overhead.mjs` on the reference machine (Apple M6, Chrome 157).

| Level | Budget per graphics call | On a 2,000-draw frame (10,000 calls) | As a share of a 60 Hz frame |
|---|---|---|---|
| `off` | 5 ns | 0.05 ms | 0.3% |
| `observe` | 25 ns | 0.25 ms | 1.5% |
| `record` | 100 ns, not counting the copy of data a write carries | 1 ms | 6% |

- The `observe` budget has to hold with the registry and shadow state on, not only the counters measured in spike S9 (6–8 ns).
- Work done once per frame (counters, timing queries) is budgeted separately: 50 µs a frame at `observe`.
- Creating an object may cost more (a call site is recorded): 5 µs per creation. A page that creates thousands of objects a frame pays for it, and that page has a bug Scanline should be reporting.

## Changed for now, to be revisited

| The specification says | The code does | Why |
|---|---|---|
| The MCP server uses the `rmcp` crate and speaks revisions 2025-11-25 and 2026-07-28, over stdio and loopback HTTP. | A small hand-written JSON-RPC server over stdio, speaking revisions up to 2025-11-25. | Quickest route to a working, tested front end. It depends only on tools, text, images and instructions. Moving to `rmcp` gains the stateless 2026 revision and HTTP. |
| Bulk data travels on a loopback binary WebSocket. | Images travel through the protocol as gzip-compressed base64. | The architecture's stated fallback. Fine for canvas-sized images; captures will need the fast channel. Spike S2 has not been run. |
| The protocol client uses types generated from the protocol definition. | Commands and events are `serde_json::Value`. | Few commands are used, each wrapped where it is called. |
| The default browser is a pinned Chrome for Testing, downloaded on first run. | The installed Chrome, Edge or Chromium is found and used. | No download step exists yet. Spike S10 has not been run. |
| Tool names are prefixed `gfx_` everywhere. | `gfx_` in MCP; bare names on the command line and in the control API. | The prefix exists to avoid clashes among an agent's tools. |
| `gfx_step`'s `observe.screenshot` takes `{scale, region}`. | It takes the screenshot command's own arguments (`max_edge`, `region`, `zoom`). | One set of image arguments to learn. |
| Every call names its session. | The session may be left out when exactly one is open. | The specification's own command-line examples leave it out. With two open, the error lists them. |
| The window (`scanline` with no arguments starts the app). | No window. `scanline serve` runs the host; the other modes start it. | Milestone 4. |
| Windows 11 and macOS. | Both, since 11 November 2026. What Windows needed that macOS did not is in "Windows", near the end. | Each has been built and tested on one machine. |
| Capability tiers, an origin allow-list, `file://` access limited to the launched file's directory. | None of these. `eval` is always available. | Milestone 7. Until then, treat a session as able to do anything the page can. |
| The probe records a rolling tail of command names, so a crash can be pinned to its last call. | Built after milestone 7: every wrapper writes its method's ID into a ring of sixteen, and a `context-lost` event (a WebGL context lost, or a WebGPU device the browser took away) carries the names, oldest first. | One store a call. A renderer crash takes the page and the ring with it, so that is still reported with no calls. Graphics calls are queued to the GPU process, so the call that did the damage may be a little before the last. |

## Milestone 2 against its exit criteria

"For every page in the matrix, the texture and buffer lists are complete (checked against known scenes), every texture can be previewed, and WebGL shadow state passes its verify check after 1,000 frames."

| Criterion | Standing |
|---|---|
| Lists complete, checked against known scenes | Met for the pages there are: the inventory fixtures have known objects and the tests count them. The matrix still lacks a Unity build and an Emscripten build. |
| Every texture can be previewed | **Met, but for multisampled textures.** Colour textures in 8-bit, float and integer formats are read back on both APIs, and compressed, depth, luminance and alpha textures by a sampling pass (see "Textures that cannot be read directly"). A multisampled texture is read through what it resolves to; the stencil of a depth and stencil texture is not read. WebGL 1 buffers cannot be read at all (the API has no call for it). |
| Shadow state verifies after 1,000 frames | Met: no drift on eight WebGL pages (raw WebGL 1 and 2, a worker, three.js, PixiJS, Phaser, Babylon.js). `node spikes/m2-verify.mjs`. |

Also from the milestone's list, and built later: WGSL reflection (not the plan's `scanline-shader` crate and `naga`: a reader of declarations in TypeScript, `shared/wgsl.ts`, because it has to run in the page), the real memory of the GPU process (milestone 5), and GPU time per pass on WebGL. Queries cannot nest, so a WebGL frame is timed in spans: the frame's query ends and another begins whenever the context starts drawing to another framebuffer, if it drew anything to the last one. `stats` lists them as `pass 0 → fbo_1`, `pass 1 → canvas`; a frame drawn in one go lists none. At most 24 spans a frame. WebGL shader reflection comes from the driver (active attributes and uniforms), which needs no parser.

WebGPU triangle counts are built too: the probe notes the topology of the pipeline each render pass last set, and counts from that. Indirect draws are left out. What a render bundle draws is counted each time it runs.

| Criterion | Standing |
|---|---|
| Replay matches on every matrix page | Met for the pages there are: eight on WebGL, and on WebGPU the two raw pages, three.js and PixiJS. At milestone 7 a Babylon.js scene with a shadow map was added, on its WebGL 2 and WebGPU engines (`fixtures/engines/babylon-shadows.html`); both replay identically. A WebGPU device in a worker, and the engines the matrix still lacks, are untried. |
| Or reports why not | Met: every capture is replayed once when taken and compared with the frame's own image, the verdict is stored with it, and replay answers carry a warning when it failed. |

The rounds were started by hand; a runner now exists (`evals/run.mjs`). Fifteen WebGPU bugs were planted later and diagnosed in round 4. |

Differences from the specification:

| The specification says | The code does | Why |
|---|---|---|
| Start-of-frame contents are recovered from end-of-frame contents and the recorded writes. | End-of-frame contents are used as they are, and the frame's writes are replayed over them. Render targets are also read before the frame. | The same result in the common cases with no reconstruction step. See the spike for where it can fail. |
| "Which draw produced this pixel" comes from a draw-ID pass with rewritten fragment shaders. | The pixel is read after every event on its target. | No shader rewriting, true values, and it gives before and after for each change. Slower: 0.3 ms an event. |
| The pass tree uses debug groups, labels, target changes and adapter knowledge. | Passes are runs of events on one target. | WebGL has no debug groups; the rest needs the page protocol and adapters. |
| The command stream is `stream.bin`. | It is `stream.zst`: the capture as JSON, compressed, with data in the blob store. | Simple, and the replay page takes it as it is. |
| Full-size intermediate targets are not stored; thumbnails of each target at pass ends are. | Only the frame's final image is stored. Intermediate targets come from replay. | Replay is fast enough that thumbnails have not been needed. |
| The replay page is at an internal URL. | It is a hidden page at `https://replay.scanline.invalid/`, a request the host answers itself and nothing fetches. | WebGPU exists only in a secure context, which `about:blank` is not. |
| A WebGPU capture is replayed onto a canvas. | The replay has no canvas: where the page called `getCurrentTexture`, it gets an ordinary texture of the same size and format. | A canvas's texture expires when the task ends, and reading a target back takes several. |
| (Not said.) How a WebGPU target is seen part-way through a frame. | The replay splits the frame at that point: it ends the open pass, finishes and submits every encoder so far, reads, then opens new encoders and a pass that loads what the old one stored and has the same state set. | WebGPU does nothing until commands are submitted, and a pass cannot be read while it is open. |
| WebGPU objects are recreated from recorded creation calls. | From the descriptors the registry already keeps for the inventory, made lossless: object references, views with their textures, layouts taken from pipelines. | One record serves both. |

Also true of what is built:

- A capture carries its own table of method names, so it stays readable when a later version numbers methods differently.
- The `draws` table holds clears and blits as well as draws, since all three change pixels. `kind` tells them apart.
- `draw_list`'s filter is a SQL condition on the `draws` table, not a language of its own. The database is opened read-only.
- Replaying a capture needs a live browser, and any open session's will do. Reading what the capture says needs none.
- Integer textures are replayed empty, and float textures on a page that has not enabled the colour-buffer-float extension. The capture's replay check then fails and says why. Luminance, alpha, compressed and depth textures are read by a sampling pass and replayed (see "Textures that cannot be read directly").
- Each replay makes a fresh context and recreates every object. Keeping one context per capture and running forwards from where it stands would make repeated questions cheaper.
- WebGL 1 buffers now have a copy kept of every upload, as the specification asks, so they can be read and captured. This doubles the memory of WebGL 1 buffers while Scanline is attached.

## Milestone 4 so far

"The hand-off journey (J2 in the PRD) works end to end on both platforms with no manual step. A recorded two-minute session of a deterministic fixture replays to the same frame hashes."

| Criterion | Standing |
|---|---|
| The hand-off journey works end to end | Works on macOS, in tests, on the planted flicker (`fixtures/bugs/b13.html`): the agent asks, the page runs, Debug freezes it and captures the frame, the recording names the three frames that flicker, and each can be taken apart. Confirmed with a person at a visible window on 11 November 2026: a real F9 press froze the page, 128 frames were kept, and the recording named the four that flicker. The tests run it headless, with the press sent as a command or as a key event. No Windows. |
| A recorded two-minute session of a deterministic fixture replays to the same frame hashes | Met on `fixtures/matrix/game.html`: 7,200 frames with 160 key presses and 103 clicks replay with all 240 fingerprints matching and every number the game holds identical to the last bit, in about six seconds. Also met for a session played live, not stepped. Tests cover a shorter one. |

Built: `request_human`, `wait` on a request, `debug`, `recording`, `take_control`, the event queue, the Debug key, the control strip, marking the frozen frame (a point, a box, a note), the flight recorder for WebGL and WebGPU, one owner of the input at a time in both directions, runs (`save_run`, `replay_run`) with divergence detection, stepping that does not wait for the display, recorded network for deterministic sessions, capture triggers (`capture(when)`), a virtual gamepad, a pointer-lock shim, and policies (`policy`).

A hotkey registered with the operating system was built after milestone 7, on macOS: while a request is open and the session has a window, the host runs `scanline hotkey <session>` as a helper process, which asks for the key with Carbon's hot key API (it needs no permission from the person, unlike watching the keyboard) and makes one press one `debug` call. It is a process of its own so that nothing it does can hurt the host, and it gives the key back at the press. `SCANLINE_HOTKEY` picks another key or switches it off. The suite proves the path with the event a press causes; a real press is in `docs/BY-HAND.md`. Not built from the milestone's list: contact sheets for anything but a recording; audio and worker time control beyond what milestone 1 has.

"Deferred destruction" is built another way. The specification keeps a resource alive after the page destroys it, until the recorder's window has moved past. Here the page's delete happens when the page asks, and the recorder reads the texture or buffer just before it does (a hook that runs ahead of `deleteTexture`, `deleteBuffer` and WebGPU's `destroy`, set only while the recorder runs). The frames that used it then replay with what it held. This leaves the page's memory and its object lifetimes exactly as the page made them. It costs a readback at each delete of something older than the current run of 30 frames, up to 64 MB an object. `fixtures/history/deleted.html` swaps a texture and a vertex buffer in the middle of a recording, on both APIs, and `tests/e2e.test.mjs` checks the frames on each side of the swap.

Building it found two older faults, both fixed. A `bufferData` call recorded during a capture lost its data: the recorder read the usage argument as an offset into the array, so any buffer filled with `bufferData` inside a captured frame replayed empty. And a WebGPU bind group layout first asked of a pipeline (`getBindGroupLayout`) during a recorded frame could not be found in the replay, which dropped every frame after it.

| The specification says | The code does | Why |
|---|---|---|
| Debug is a global hotkey registered with the operating system. | The probe takes the key (F9 by default) in the page, ahead of the page's own listeners, so the page never sees it. | No window process exists yet to own a hotkey. It works while the page has the keyboard, pointer lock and fullscreen included, and not when another window does. |
| The control strip is part of a native window (egui) attached to the game window. | It is a popup window of the supervised browser itself, placed under the game's window, showing a page the host serves and talks to through the protocol. | No second toolkit, the same on every platform, and it can be driven in tests: `strip(press: "debug")` clicks the real button. It is not attached: it does not follow the game's window when that is moved, and opening it takes the keyboard for a moment (the host gives it straight back to the game). The capture viewer and graphs of milestone 7 may still want a native window. |
| While the agent owns input, the person's is ignored with `Input.setIgnoreInputEvents` or a probe filter. | The probe filter. The host tells the probe which events are its own just before sending them (keys by code, pointer and touch events by where they land); the probe stops every other trusted input event ahead of the page's listeners and the input recorder. | `Input.setIgnoreInputEvents` drops injected events too (spike S4). The person pressing the same key, or clicking the same pixel, within a second and a half of the agent would get through. |
| Ownership is human, agent or none, changed only by explicit action. | The same: `request_human` gives it to the person, `take_control` to the agent, a Debug press or `take_control(release: true)` to nobody, in which state both reach the page. | |
| The flight recorder keeps the last N frames. | It records in runs of 30 frames, each beginning with a snapshot of the state, and drops whole runs, so it holds between N and N + 30. | A recording has to be replayable from its first frame, which needs the state as that frame began. Snapshotting every frame would cost too much; every 30th is cheap. |
| Resources destroyed inside the window are kept alive until they leave it. | Not done. An object the page drops is held, but one it deletes is gone, and is empty in the replay. | WebGL would need the contents read at the moment of deletion, WebGPU the destroy deferred. |
| The recording has thumbnails taken as the frames went by. | None are taken live. `recording` replays the frames once and reads each one's picture then. | Reading the canvas every frame stalls the page. Only the frozen frame has a picture from the page, so only it checks the replay. |
| `record` is an overhead level. | The recorder is started and stopped by `request_human` and Debug at whatever level the session has. | It is on only while a person is hunting something. |

| Capture triggers: now, next frame, on Debug, on an error, on a frame-time threshold, on a page event. | `capture()` is now; Debug is the press. `capture(when: {error}, {frame_ms_over}, {mark}, {expr})` starts the flight recorder, runs the page until the condition is met, and then does what a Debug press does: the frame that met it becomes a capture and the frames before it a recording. It queues `capture_ready`, not `debug_pressed`, and leaves the input with whoever had it. | An error is known only once its frame has passed, so without the recorder the frame that raised it would already be gone. |
| The person annotates the frozen frame: a click, a dragged box, a typed note. | After a Debug press by the person the probe takes clicks and drags on the page before the page's own listeners see them, and emits each as an `annotation` event in canvas pixels; a thin outline shows the person what they marked. The strip grows a note field whose text arrives as an `annotation` with a note. All of it ends when the page moves on. | The marks come after the press, so they are events of their own and not part of `debug_pressed`. The outline is a `div` added to the page while it is frozen and removed after: a change the page could see if it looked. Tested with protocol input standing in for the person; the look of it is on the by-hand list. |
| Virtual gamepads through a shim over `navigator.getGamepads`, with connect and disconnect events; a real pad passes through and is recorded. | Built so. A pad the agent sets (`input` with `{gamepad: 0, buttons, axes}`) is an object inheriting from `Gamepad.prototype` with its own values, returned in its slot; a real pad fills the others and is sampled each frame and recorded when it changes. Pad states are rows in a run and are set again on the same frames in replay. | The connect and disconnect events are made by the probe, so they are not trusted events. No real pad was available to check the pass-through: it is on the by-hand list. |
| Pointer lock: protocol mouse moves if they deliver usable deltas under lock, otherwise a probe shim that grants lock and delivers moves with explicit deltas. | The shim, and only when asked for: `launch(pointer_lock: "shim")`. `requestPointerLock` is granted without a gesture, `pointerLockElement` says so, `exitPointerLock` gives it up, and `input` with `{pointer: "move", dx, dy}` dispatches a `mousemove` with that movement on the locked element. Without the shim a relative move is refused with the reason. | The browser's own lock needs a real gesture in a focused window, which a headless session cannot give, and the protocol cannot inject a relative move. The shim's moves are not trusted events and the cursor is neither hidden nor confined. The browser's own lock was checked with an injected click in a headed window (`spikes/s4-input.mjs`, with the page brought to the front first): it is granted, as is fullscreen, when the window is in front, and refused when it is not. Scanline leaves its window where it is, so a refusal is queued as a warning event that names the shim. |
| In-page policy scripts. | `policy(source, frames)`: the function runs in the page once a frame with the state the page provides (and whatever it reads from globals), and answers `{keys_down, events, log, stop}`. The host holds the keys and sends the events as real input, then steps one frame, without waiting for the display. | The function decides in the page; the input still goes through the browser, so the page sees trusted events and a run records them. About a millisecond or two a frame. |

About runs and deterministic sessions:

| The specification says | The code does | Why |
|---|---|---|
| A deterministic session has a seeded random source and a fixed virtual timestep. | Also a fixed origin: page time starts at 0 and the date at 1 January 2026 (UTC). | The clock used to start from whenever the page happened to load, so two runs read times a few milliseconds apart. A game that used the time itself, not only the difference between frames, drew different frames. |
| Divergence is found by comparing per-frame draw counts and thumbnail hashes. | A fingerprint (a hash of the canvas, the draw count, the call count) is taken every 30th frame of a deterministic session, and a replay is compared with them as it goes. | Reading the canvas every frame would stall the page. A replay stops within 30 frames of where it parted. |
| Replay is unpaced. | `step` and `replay_run` have a fast mode that runs each frame as the next task instead of waiting for the display. | Stepped frames otherwise run at the display's rate, so replaying two minutes took two minutes. |
| Network responses are recorded and replayed at the frame they first arrived. | Built for the page itself. In a deterministic session every response is held at the host as it arrives (the protocol's `Fetch` domain, at the response stage), its body read, and then handed to the page between two frames: the probe's frame gate takes a hold, the response goes in, the page's event loop is given a few turns, and the hold is let go. The frame that had just ended is kept with the response. A replay intercepts requests instead, answers each from the run's kept responses, and hands each over when the replay has reached its frame. | "The frame it arrived on" has to mean the same thing in both, so a response always goes in with the page held between frames. A hold is not a pause: `run_until` and a step in progress carry on when it is let go, and nothing waiting on the page is told. It costs a few milliseconds a response while recording. Not kept: responses over 24 MB, what a worker fetches, and WebSocket traffic. On the fixture made for it (`fixtures/matrix/loader.html`, which draws by a number the server changes every time) a replay gives the same numbers on the same frames and every fingerprint matches. |
| A run records keyboard, mouse and touch. | Also a gamepad's states and the pointer-lock shim's relative moves. | |

Fast frames are not presented one by one, so a page that depends on the browser clearing its drawing buffer between frames draws over its last frame in fast mode. Its fingerprints then differ from a run recorded at normal speed, and the replay reports that as a divergence.

While adding fast mode a fault was found in frames the probe runs by hand (which it already did for a hidden window): each was stamped with the real time, which the browser coarsens to 100 µs, so two run back to back could be taken for one. They are now numbered.

Measured cost of recording, with `node spikes/s9-overhead.mjs` (Apple M6, Chrome 157), against a budget of 100 ns per graphics call:

| API | Calls per frame | Recording, per call | A 2,000-draw frame costs |
|---|---|---|---|
| WebGL 2 | 10,002 | about 220 ns | 2.2 ms more |
| WebGL 2 | 50,002 | about 205 ns | |
| WebGPU | 4,008 | about 430 ns | 1.7 ms more |
| WebGPU | 20,008 | about 136 ns | |

Over budget on both. Most of it is the row of state built at every draw (WebGL copies the program's uniform values each time). Building those rows when the recording is taken, from the calls, would bring it down; that is not done. The same run measured `observe` at 22 to 55 ns a call, noisier than the 17 measured before, on a machine that was doing other work.

A frame taken from a recording is replayed from the recording's first frame. That is simple and exact, and it makes questions about late frames of a heavy scene slow: a keyframe every so often would fix it.

## Milestone 5 so far

"Pixel history is correct on hand-checked fixtures including `discard`, written depth and MSAA. The planted performance and memory bugs are diagnosed by an agent."

| Criterion | Standing |
|---|---|
| Pixel history correct on hand-checked fixtures | Met. Correct on the planted bugs (the culled crates, the depth clear, the scissor left on, the glass before and after the crates), and on `fixtures/history/webgl2.html`, a scene made for it whose answers are written down in `fixtures/README.md`: a disc whose quad's corners are discarded, a ramp whose shader writes its own depth and so beats the floor on one side and loses on the other, and a quad behind the floor. Built: `pixel_history` (WebGL; rejected fragments need WebGL 2), `geometry` (WebGL 2), `compare`, `lint`, `shader_analysis`, `profile` (WebGL 2), the `overdraw`, `wireframe`, `draw_id`, `depth`, `stencil`, `mip` and `nan` views (WebGL), and the GPU process's real memory beside the estimates.

| The specification says | The code does | Why |
|---|---|---|
| Pixel history finds candidates with a draw-ID pass, then replays each candidate about six times. | One replay of the frame. Before each draw the same draw is issued again with every write masked and the scissor box shrunk to the pixel, inside an occlusion query: once with all tests off, then with culling, depth and stencil on one at a time. | Nothing is written, so the frame carries on untouched and every draw is tested in one pass. No shader is rewritten. |
| Pixel history gives depth before and after. | Colour only. | WebGL cannot read a depth buffer back. |
| `discard` is detected by replaying with a constant fragment shader. | Detected, in the same single replay: the draw is issued once more with its own vertex shader and a fragment shader that keeps every fragment, inside one more query. A draw whose shape covers the pixel while none of its own fragments survive there had them discarded. | The stand-in program is linked from the vertex shader's source with attributes at the same locations, and given the page's uniform values and uniform block bindings before each use. If it will not link, the history says the two cases could not be told apart. |
| Targets are textures or the canvas. | Also a framebuffer whose colour is a renderbuffer, named by its handle (`target: "fbo_1"`). A multisampled one is resolved into a scratch framebuffer of the same format each time it is read. | A renderbuffer target was being taken for the canvas, so its events were listed in the canvas's history and never read. Found by the multisampled fixture. A blit now says where it copies from, in `draw` and at the end of a pixel's history. |
| Static shader analysis uses a parser (`naga`, ANGLE's translator). | A reading of the text: words and braces. It counts sample calls, loops with constant bounds, branches, `discard`, and inputs never mentioned again. | Enough for "64 samples in a loop". It does not follow function calls, so a sample inside a helper called from a loop is counted once. |
| Overdraw is counted by replaying into a float target with a constant output and additive blending. | It is counted in the stencil buffer: every draw adds one wherever a fragment lands, or only where it also passes the depth test, and the counts are then drawn out a level at a time and read. | No shader has to be replaced. It works for the canvas only, not for other targets, and not for a frame that uses the stencil test itself. It counts to 64. |
| Per-draw timing is amplified and attributes time to the vertex, fragment and texture work. | Each draw is issued 16 times inside one timer query during a replay, three replays are run, and the middle figure is kept. Before and after each timed draw a pixel of its target is read back, which makes the GPU finish. No attribution. | Without the read, a timer counted whatever the GPU was still doing: on the first slow fixture the one expensive draw was charged again, in full, to each of the eight draws after it. `finish()` does not wait in this browser, and reading from another target does not either. A target with no colour to read (depth only, multisampled) is not waited for. |
| The depth view reads the depth attachment. | WebGL cannot read a depth buffer back, so the replay copies it with a blit into a depth texture, then draws a quad from that texture that writes each depth as a 24-bit number in a colour, and reads the colours. The canvas's depth format is the browser's choice, so each likely one is tried until the blit is accepted. | Checked on the hand-made scene, where the depths are known: 0.5, 0.4, what a shader wrote, and 1 where only the clear reached. WebGL 2 only. |
| Geometry and vertex stage output. | `geometry(capture, draw)`: each attribute the program reads with its first values, read from the buffers as they stand at the draw; then the clip-space position of every vertex the draw names, and from those how many primitives would reach the rasteriser: not NaN, not behind the eye, not wholly outside the view volume, not of no area, and which way they face against the culling state. | WebGL 2's transform feedback takes only points, lines and triangles from `drawArrays`. So each vertex is run through the program's own vertex shader once, as a point, and the primitives are put together from the draw's mode and indices. The first instance only, and the first 60,000 vertices. |
| A draw-ID view. | `view(draw_id)`: every draw is issued with its own vertex shader and a fragment shader that writes the event's number, with blending off, so the target ends up holding who owns each pixel. It lists each owner's pixels and box, and the draws that own none. | It is about shapes: a discard in the page's shader, or a depth the shader writes, is not seen. It says so. |
| A stencil view: "a pass per bit, or per value, with the stencil test, into a colour target". | `view(stencil)`: the target's stencil buffer is copied by a blit into a framebuffer of the replay's own, and a quad is drawn through the stencil test eight times, once per bit, each adding that bit's worth to a colour. The answer lists every value that occurs with its pixel count and box, and the value at one pixel. Checked against `fixtures/history/views.html`, whose values are worked out by hand in its source. WebGL 2. | |
| A mip view: "bind a texture whose mips are distinct solid colours in place of the original". | `view(mip)`: the frame is replayed with each level of every mipmapped 2D texture (or of one named texture) filled with one colour. It counts the pixels that are exactly one level's colour, which is exact for unlit, unblended sampling with a nearest mip filter and a lower bound otherwise; the picture is there for the rest. Checked against the same fixture. | A lit or tinted surface shows a level's colour multiplied by something, which no count can undo. |
| A NaN view. | `view(nan)`: a float target is read as floats and each pixel marked NaN or infinite. For an 8-bit target it says a NaN cannot be stored there and names the frame's float targets. | |
| Real GPU-process memory and reconciliation. | `memory` reports the GPU process's physical footprint as the operating system counts it (`proc_pid_rusage` on macOS, the resident set on Linux), and a diff of two snapshots says how far it moved and whether that bears the estimated growth out. | It is the whole process: every page, the compositor and the process itself. Only the change between two snapshots says anything about one page. On the leak fixture 400 textures estimated at 100 MB moved it by about 80 to 120 MB. |
| `gfx_compare` gives per-target image differences. | Built: the final pictures from what each capture kept, and each offscreen target both frames drew to (up to six) by replaying both captures and reading the target as the frame left it. Targets are matched by handle, or by the order the frames first drew to them where they are the same size. | Intermediate targets are not stored, so this part needs an open session to replay in; without one `compare` says so and gives the rest. A float target is compared as it is shown, clamped to 0 to 1. |

Translated shaders are kept: a WebGL capture holds, for each shader the frame used, what the browser compiled its source to (ANGLE's translation, from `WEBGL_debug_shaders`), in the `translated` column of its `objects` table, and `shader_analysis(handle, capture)` writes it to a file. A shader the page deleted before the capture was taken has none: a deleted shader cannot be asked, and asking every shader as it is compiled would cost a round trip to the GPU process each. WebGPU has no call that gives the translation of a WGSL module.

Not built from the milestone's list: attribution of GPU time within a draw, and exact error attribution beyond what a capture's rejected calls give. The analysis of WebGPU captures was not built at the milestone; it was built after milestone 7, and "WebGPU analysis" below says how.

The depth and stencil views are built for WebGPU. The replay notes which depth-stencil texture each colour target was drawn to alongside. Depth is read by a pass that samples that texture into a float target, which works for `depth24plus`, a format a copy cannot read; stencil is copied out. A pass that discards its depth and stencil when it ends, as most do, is replayed keeping them. Checked against `fixtures/history/views-webgpu.html`, whose depths and stencil values are worked out by hand in its source.

Tracing is built as `trace(frames)`: the browser's own trace (the protocol's Tracing domain) is recorded while that many frames are stepped. It reports how long the GPU process's main thread was busy, the busiest threads, what the GPU process spent its time on by slice name, buffer swaps, and the path of the whole trace, which Perfetto opens. A headless or stepped session presents to no display, so presented and dropped frames as a compositor counts them are only reported when the browser gives them.

### The page protocol and adapters against the specification

| The specification says | The code does | Why |
|---|---|---|
| `frame.begin()` / `frame.end()` are explicit frame markers for loops not driven by `requestAnimationFrame`. | They are accepted and counted, and `page` says the page marks its own frames. Frames are still the browser's frame callbacks and timers. | A loop on timers already steps. One on `MessageChannel` cannot be held by the frame gate at all, so its markers could number frames but not pause them. |
| `time.provide({pause, resume, step, setScale})`: Scanline calls these in place of, or as well as, its frame gate. | They are kept and called only when asked: `page(call: "time", action)`. | The frame gate already stops the browser's frames and clock exactly. Calling the engine's pause as well would leave a stepped frame with nothing moving in it. |
| `time.deterministic({seed, fixedDt})` is called by Scanline at start-up. | The page calls `time.deterministic(fn)`: in a deterministic session `fn` is called at once with the facts, which are also returned; otherwise it returns null. | The probe runs before the page, so there is nothing to call at start-up. The page asks when it is ready to seed. |
| `checkpoint` enables quick rewind. | `page(call: "checkpoint")` keeps what the page's `save()` returns, as text, and `page(call: "restore")` hands it back. The browser's clock and frame number do not go back. | It is the game's state as the page chose to save it. Going back to an exact frame is what a run replay does. |
| `gfx_live_view` takes the views of `gfx_view` as well as registered ones. | Registered views only. | The built views (overdraw, wireframe) work on a capture's replay, where draws can be issued again. On the live page they need substitute shaders. |
| Generated names are marked as generated. | The page's and the engine's names are shown in «». Names Scanline makes itself (`batch 3 (2 objects)`, `scene Yard, camera Main`, `filter pass 1`) are built from the engine's objects and are inside «» with them. | A group's name is one string by the time it reaches a capture. The object's own fields (in `entity_detail`) are the engine's, unaltered. |
| Phaser's adapter is for the engine in the specification's repository (`window.game`, the frame graph, `game.hold()`). | It is for Phaser 4 as published (4.2.1): `window.Phaser`, the WebGL renderer's render nodes and batch handlers. | That is the Phaser a page under test loads. The engine-side changes listed in section 2.1 were not made: that repository was not touched. |
| An adapter uses the engine's own pause, step and statistics where they exist. | It reports the engine's statistics (`renderer.info`, the stage and scene trees, batch counts and why batches ended) in `page`, and registers a few engine settings as controls on three.js. Time is left to the frame gate. | As for `time.provide`. |
| three.js: passes for each post-processing pass, named by render target and pass class. | Every `render` call is a group named for its scene and target, which covers shadow maps, render targets and full-screen quads. An `EffectComposer` is not wrapped, so its passes are named by their quad, not their class. | The composer is not reachable from the renderer; the page would have to hand it over. |
| PixiJS: passes for masks and render textures. | Filter passes, renders to a texture and unbatched objects are groups. Stencil and colour masks change state without drawing and appear as the reason a batch ended. | |

How the adapters find their engine, and what that costs:

- three.js announces itself to `__THREE_DEVTOOLS__`, and PixiJS calls `__PIXI_APP_INIT__` and `__PIXI_RENDERER_INIT__`, so the probe defines them.
- Phaser announces nothing. The probe watches `window.Phaser` with an accessor, and puts a setter for `cameraRenderNode` on `Object.prototype`: the one property that only Phaser's WebGL renderer assigns. That is how a Phaser bundled as a module, which sets no global, is found. It is listed among the changes a page could observe, and is absent in unmodified mode with everything else here.
- Every wrapped engine function runs the engine's own function with its own arguments and result. If the adapter's part throws, the adapter switches itself off and says so in `page`.
- Phaser draws when a batch is flushed, not when an object is submitted, so its adapter records which game objects went into which part of each batch and reads it back when the renderer issues the draw.

A fault found on the way: a WebGPU capture of a PixiJS frame did not replay once the scene used textures made from a canvas. PixiJS passes its own style object as the sampler's descriptor, and the copy the probe keeps of a descriptor followed it to the canvas element. The replay now ignores a member of a descriptor that is not a GPU object, as the browser does. The CLI also panicked when its output was piped to something that stopped reading (`| head`); it no longer does.

|---|---|---|
| A patched shader is compiled into the page's program, which is relinked; the page's uniform locations are then translated on every `uniform*` call. | The page's program is left alone. A second program, the shadow, is linked from the edited source with every attribute at the location it had. Before each draw that uses the page's program the shadow is made current and given the page's uniform values (only when one has changed); after it, the page's program is made current again. | No translation on the hot path, nothing of the page's is invalidated, and reverting is simply to stop. ### Overhead, measured again on 11 November 2026

The gate and the uniform watch were added to the generated wrappers and the WebGL tracker, so `node spikes/s9-overhead.mjs` was run again. The result is not what the budgets ask for, and not fully understood.

On the 2,000-draw WebGL 2 page (10,002 calls a frame), three rounds each, the probe built from three commits and measured in one sitting:

| Probe as of | `off`, per call | `observe`, per call |
|---|---|---|
| Milestone 2 (`cee2b2f`) | 26 ns | 51 ns |
| Milestone 3 (`ee30344`) | 10 ns | 63 ns |
| Now | 12 ns | 82 ns |

- The budgets are 5 ns at `off` and 25 ns at `observe`. Both are exceeded.
- The same build measured 71, 82 and 94 ns in three runs an hour apart, and `off` moved between 10 and 26, so differences of 10 to 15 ns here are noise. The machine was not idle (load average 3.7).
- Milestone 2's code was recorded at about 17 ns when it was written and measures 51 ns now. Either the machine or the browser differs from then, or that figure was optimistic. The absolute numbers should not be trusted until this is measured on a quiet machine.
- What does hold: within one sitting, `observe` costs about half as much again as it did at milestone 2.
- It is not the draw gate or the uniform watch. With either removed the figure stays inside the noise (82 and 100 against 94).
- The 10,000-draw page gives nonsense (a spread of 1.2 ms between runs with no probe at all), so it is left out.

Not done: finding where the growth since milestone 2 comes from. It wants a profiler on a quiet machine, not more runs of this spike. `--api`, `--draws` and `--modes` were added to the spike to make that easier.

Two faults found by running the journey: `experiment` never reported GPU time (it read the wrong field of the probe's figures, and its test did not look), and it left the canvas showing the experiment's last frame, so a screenshot taken next was of the clipped frame. Both fixed; the journey test covers them. The static shader reading now follows a loop bound to a named constant (`const int SAMPLES = 64`, `#define`, WGSL `const`).

- **A depth texture used as a render target made its framebuffer incomplete in the replay.** A depth texture's contents are not read back, and the replay did not give it storage either, so every draw to Babylon's shadow map was rejected. The replay now allocates it empty, in its own format; the frame's shadow pass fills it.
- **A WebGPU command encoder made before the captured frame was ignored, and the frame with it.** Babylon makes the next frame's encoder as soon as it has submitted this one's. The capture now makes such an encoder at the point it is first used, and says so in a note. Anything encoded on it before the frame began is not in the capture; the replay check shows whether that mattered.

|---|---|---|

## WebGPU capture: what it does not do

- Geometry, and which test turned a draw away, for a draw inside a render bundle.
- External textures. The calls that use them fail in replay and the summary says so.
- The contents of stencil and multisampled textures. They are empty in replay; a pass normally clears them.
- Buffers and textures the GPU wrote in an earlier frame (a simulation stepped by a compute pass) are read before the frame begins, with the render targets: every storage buffer and storage texture, up to 256 MB in all. Read after the frame they would hold the frame's own step, and the replay would take it twice. Past the budget the capture says so, and the replay check shows whether it mattered.
- More than one device in a capture. Calls on another device's objects are left out.
- A call rejected in replay is found by wrapping every call in an error scope. WebGPU reports most errors when an encoder is finished, so the call named is `finish`, with the browser's message saying which pass call was at fault.

## Textures that cannot be read directly

A compressed texture, a depth texture and (on WebGL) a luminance or alpha texture cannot be attached to a framebuffer or copied to a buffer as texels. They are read by drawing them: a shader of the probe's own draws one level, texel for texel, into a target that can be read. A frame that only samples such a texture (a shadow map drawn once, a compressed atlas loaded at start) used to replay with it empty.

- **WebGL** (`probe/src/gl/sample.ts`). The draw uses the page's context, and everything it changes is put back from the state mirror; `resource(ctx, verify: true)` still matches afterwards. Depth is written as 24 bits across three channels. sRGB blocks are drawn to an sRGB target on WebGL 2, so the bytes read are the texture's own.
- **A WebGL capture replays a compressed texture as the texels it decodes to**, in an 8-bit RGBA texture (sRGB where the blocks are), since WebGL has no call that reads blocks back. The frame samples the same values. A frame that itself uploads to that texture with `compressedTexSubImage2D` has that call rejected in replay, and the replay check says so. Signed and HDR block formats are clamped to 0 to 1.
- **Depth in a WebGL capture** is uploaded on WebGL 2. WebGL 1 takes no data for a depth texture, so the replay draws it in with `EXT_frag_depth`; without that extension the texture is empty, as before.
- **WebGPU** (`probe/src/gpu/sample.ts`). A compressed texture is copied as its blocks for a capture, which the replay writes back as they are, and drawn to be looked at. Depth is copied where the format allows (`depth16unorm`, `depth32float`, the depth of `depth32float-stencil8`) and drawn where it does not (`depth24plus`). `TEXTURE_BINDING` is added to the usage of `depth24plus` textures so that they can be drawn; it is declared with the other changes. The replay fills a depth texture by drawing a triangle whose fragments take their depth from the captured values.
- Depth render targets are read before the frame, as colour targets are, so a frame that loads depth an earlier one drew replays from the right start.
- Not read: multisampled textures, stencil, and 3D compressed textures.

## The WebGPU bugs, and what planting them found

The planted-bug scene was written again in raw WebGPU (`fixtures/bugs/scene-webgpu.js`), with fifteen mistakes of the kind a WebGPU page makes (`evals/bugs.json`, `w01` to `w15`). Each reproduces (`tests/bugs.test.mjs`), and Scanline is held to stating the cause of each in a capture's summary or one further command (`tests/findings.test.mjs`). Agents were then given them (round 4, `evals/results/README.md`): fifteen of fifteen diagnosed, in a median of 8 commands. The bugs and the findings below were written together, so that round shows these causes are found, not how Scanline does on a mistake nobody has thought of.

Most were already answered by what was built. Planting them found these gaps, now closed:

- **A pass that ends with `storeOp: "discard"` replayed wrongly.** The replay keeps what every pass draws, so that it can be read; a target the page's pass threw away was full in the replay and empty in the page. The replay now empties such a target when the pass ends, as the browser does, and the capture says when a later draw samples it.
- **Mip levels that were never written.** The probe now follows which levels of a WebGPU texture have been written (an upload, a copy, a pass that draws to it), the inventory says `9 levels (only level 0 written)`, and a capture names the draws that sample such a texture. A texture a compute pass may write is not judged.
- **Translucent colours written unblended to an opaque canvas.** The canvas shows as if alpha were 1, so nothing looks wrong until the colour does. A capture counts the pixels of an opaque WebGPU canvas that end the frame with alpha below 1 and says where.
- **The viewport finding** looked for a run of events that all used one viewport. A WebGPU pass's clear is listed with the whole target, so the run never matched; the draws now decide. It is reported only for a viewport that starts at the target's corner, which is what one left over from another target looks like: a viewport placed elsewhere in the target was put there on purpose.
- **A uniform buffer written short of what its shader reads.** `draw` gives each member's byte offset, and says when the page has only ever written part of what the struct covers: the usual sign of a layout written without WGSL's padding.

## State set up long before the frame

A capture begins from the state the frame began with. Three parts of that state were missing for WebGL 2, and a page that used them replayed wrongly or not at all:

- **Numbered buffer binding points.** `bindBufferBase` and `bindBufferRange` bind a uniform block's buffer, or a transform feedback target, to a numbered point, and a page often does it once at start. The capture now asks the context for every such binding (and its offset and size) as the frame begins, for uniform buffers and for each transform feedback object, and the replay makes them again. The tracker does not follow these calls; they are read when a capture is taken.
- **Transform feedback varyings.** What a program writes by transform feedback is fixed when it is linked. The capture reads the names and the mode from each linked program, and the replay sets them before it links.
- **Buffers that transform feedback writes.** A frame that steps a simulation with transform feedback reads what the last frame left. Such buffers (any that has been bound as a feedback target, up to 64 MB each) are read before the frame, as render targets are. Read after it they held the frame's own step, and the replay took it twice.

A draw made with `RASTERIZER_DISCARD` on is no longer listed as "changed no pixels": it is not meant to.

## Assertions for a test run

Built after milestone 7. The build plan names "CI assertions and baselines" for after 1.0 and the specification says nothing more, so the design is this project's. One command, `assert`, checks the running page: the canvas against a baseline PNG (`update: true` saves it; `tolerance` and `max_changed` give it room; `region` checks a part), one pixel against a colour, the console against "no errors", and the recent frames against budgets for draws, triangles, API calls, GPU time and CPU time. It answers pass or FAIL for each and, from a shell, exits 2 when anything fails. A failed baseline writes the canvas as it is and a picture of where it differs. Baselines are plain PNG files wherever the caller keeps them (the files tier applies); nothing is stored in Scanline's own directory.

Not built: baselines of anything but the canvas (a capture's draw list, a texture), and a report in a format a CI system reads (JUnit). `--json` gives every check as data.

## Loops that are not on frames or timers

Built after milestone 7 (it was a known limit). A page can run its loop on a `MessageChannel` (a message to itself is a task with no delay) or on `scheduler.postTask`, and neither was held by a pause. Now, while the clock is frozen (paused, stepping, or a deterministic session), a message posted on a port is kept and sent at the next frame's drain, so such a loop takes one turn a frame; a message already on its way when the page is paused is handled at the next drain too. `scheduler.postTask` and `scheduler.yield` are timers of the probe's own at all times (priorities are not kept). While the page runs freely, messages go straight to the browser. A handler set as `onmessage` is followed so that what it draws is kept for the frame's picture; one added with `addEventListener` is paused and stepped all the same, but a frame it draws may be captured without its picture, and the replay check says so.

## The native-capture profile

Built after milestone 7 (the architecture lists it as "later"). `launch(profile: "native-capture")` starts the browser with its GPU sandbox and GPU watchdog off, Metal capture allowed in its environment, and Dawn told to pass the page's labels to the native API unrenamed. ## A recording as a video

Built after milestone 7 ("frame sequences as video" in the build plan's list for after 1.0). `recording(recording, video: true)` writes the recording's frames as a WebM file beside its contact sheet, for the person to watch or to attach to a report. The frames are already made by replaying the recording; with `video` each is also given to the browser's own VP8 encoder (WebCodecs) in the replay page, and the WebM container is written by hand (`replay/src/video.ts`). 60 frames a second by default, scaled down by whole steps to at most 960 on the longest edge, opaque. ## The Babylon.js adapter

Built after milestone 7 (the build plan puts it after 1.0). Babylon announces itself to nobody, so the adapter finds a scene the way Phaser's finds a renderer: a setter on `Object.prototype` for `_renderingManager`, which every Babylon scene assigns as it is constructed. From the scene it finds the classes it needs by looking at what the scene holds each frame, and wraps on their prototypes: `Scene.render`, `RenderTargetTexture.render`, `Mesh.render`, `ShadowGenerator._renderSubMeshForShadowMap`, the post-process manager, sprite managers, particle systems, layers and effect layers. Each mesh draw carries the mesh's class, name and material, and whether it is a shadow-map draw. The scene's switches (shadows, lights, textures, post-processes, fog, wireframe) and the hardware scaling level are controls.

Tested with 9.35.0 on the WebGL 2 and WebGPU engines, on `fixtures/engines/babylon-shadows.html`. Not named by mesh: draws made by a depth renderer, an outline or bounding-box renderer, or a GUI texture. They are grouped by their pass.

## The PlayCanvas adapter

Built on the PC on 11 November 2026, against PlayCanvas 2.24.0. A PlayCanvas application announces itself to a devtools hook if one is there when it is made (`globalThis[Symbol.for('playcanvas.inspector')].register(app, { version, … })`), so the adapter is that hook, and passes each call on to a hook that was there first. For a version from before the hook there is also a setter on `Object.prototype` for `defaultLayerWorld`, which every application assigns as it sets itself up; such a version does not say which it is.

PlayCanvas draws a frame as a list of passes and, inside a pass, loops over mesh instances, setting each one up and then calling the device's draw. It has no function that is "draw this mesh instance". So the adapter listens for the last thing the loop does for a mesh instance before it draws (`Renderer.setMeshInstanceMatrices`) and names the draw that follows (`GraphicsDevice.draw`). The frame is `AppBase.render`; the passes are found after `Renderer.buildFrameGraph` and wrapped at `FramePass.render` and `RenderPass.render`. A camera's pass is named for its layers and camera, a shadow map for its light. Each draw carries the mesh instance's node name and path, its material, its instance count, and whether it is a shadow-map draw. Controls: lights casting shadows (the engine has no one switch, so this stops every light that was casting and starts those same lights again), the time scale, the exposure and the device's pixel ratio.

Tested on `fixtures/engines/playcanvas.html` on the WebGL 2 and WebGPU devices (`tests/protocol.test.mjs`), and on WebGL 2 in the probe's own state-mirror and replay tests. Not named by object: a draw made without a mesh instance, such as the full-screen quad of a post effect. It is grouped by its pass. Not tried: PlayCanvas's post effects, its Gaussian splats, XR, and any version but 2.24.0.

**What PlayCanvas found in Scanline itself**, each fixed, and none about PlayCanvas alone:

- **A buffer written through a mapping made before the capture began was captured empty.** PlayCanvas maps the buffers it will write the next frame's uniforms into as soon as the last frame is submitted. A capture learned of mapped ranges only while it was recording, so it never saw those, and what the frame wrote through them was lost; it then tried to copy from the buffers afterwards, when the engine had mapped them again, which the browser refuses with a warning in the page's console. The replay drew with zeros and did not match. The probe now remembers every mapped range from the moment it is handed out, and never copies from a buffer the page has mapped.
- **Reading a texture by drawing it sampled the wrong texture unit.** The probe bound the texture to whichever unit the page had active and left its own shader sampling unit 0. Every page until now happened to leave unit 0 active. PlayCanvas does not, and keeps a shadow map there, so the browser rejected the draw and said so in the page's console. The shader now samples the unit the texture was bound to.
- **Integer textures were not replayed on WebGL 2**, and a note said so. PlayCanvas keeps its lights in one (R8UI), in every frame. They are replayed now (one, two and four channels, 8, 16 and 32 bits, signed and unsigned; not RGB10_A2UI).

## Render bundles

Built after milestone 7. The probe keeps what is recorded into every bundle encoder (each call, with the objects it names by reference), and the list becomes the bundle's when the encoder is finished. A bundle is a registry object like any other (`bnd_N`, in `resources`).

- A capture holds every bundle its frame runs, whenever it was built, with the pipelines, bind groups and buffers it uses. The replay records it again, call by call.
- `executeBundles` stays one event, so event numbers do not change. `draw` lists the draws inside, each with its pipeline. `stats` counts what a bundle draws in each frame it runs.
- Where an analysis issues draws its own way (draw_id, overdraw, wireframe, mip), the replay does not run the bundle: it issues what the bundle recorded on the pass, which draws the same, and each draw goes through the analysis. Their pixels belong to the bundle's event. `profile` times a bundle whole.
- Not done for a draw inside a bundle: `geometry`, and the tests in `pixel_history` and `draw` ("which test rejected it"). They are worked out per event, and a bundle's event is several draws.

Checked against `fixtures/history/bundles-webgpu.html`: one bundle built before the first frame (two draws, one with a pipeline of layout `'auto'`), one built every frame, and a draw straight on the pass.

## WebGPU analysis

Built after milestone 7, for WebGPU captures: `pixel_history`, "which test rejected this draw" in `draw`, `geometry`, `profile`, uniforms by name in `draw`, and the `draw_id`, `overdraw`, `wireframe`, `mip` and `nan` views. Checked against `fixtures/history/analysis-webgpu.html`, whose every count is worked out by hand (`tests/webgpu.test.mjs`), and run on three.js, PixiJS and Babylon.js on their WebGPU renderers.

WebGL lets a debugger switch a test off or swap a program between two draws. WebGPU fixes all of that in a pipeline, which cannot be changed. So each of these makes variants of the page's pipelines from the descriptors the capture kept, and issues the page's draws with them. The specification says what the commands return; how they are made on WebGPU is this project's.

| Specification | Built | Why |
|---|---|---|
| (Not said.) How a pipeline is rebuilt when it was made with layout `'auto'`. | Its bind groups are made again from the page's descriptors against the variant's own layouts. | A pipeline made with `'auto'` takes only bind groups made from its own layouts, and a variant is another pipeline. Most samples and some engines use `'auto'`. |
| Draw-ID and overdraw replace the fragment shader. | They keep it. A second fragment entry point is written into the page's module: it calls the page's own, then replaces the colour. The event's number arrives as the blend constant, so one variant serves every draw of a pipeline; overdraw adds one with an additive blend. | A different fragment shader uses different resources, which changes an `'auto'` layout and breaks the bind groups. Calling the page's keeps them, and keeps its `discard`: a fragment the shader throws away owns nothing and is not counted, which the WebGL views cannot say. |
| WGSL reflection. | A reader of this project's own (`shared/wgsl.ts`, used by the replay page and by the probe), of declarations only: structs, resource variables, entry points, and the names each function mentions. It lays buffers out by the language's rules and writes the extra entry points. | The browser tells a page nothing about a shader. A full WGSL compiler in the page would be a large dependency for the little that is needed. A module it cannot follow leaves its bindings unnamed and its draws out of draw_id and overdraw, and the result says so. |
| Geometry reads the vertex shader's output with transform feedback. | WebGPU has none. The draw's vertices are drawn as points to a float texture by an entry point that calls the page's vertex shader, puts each vertex on a pixel of its own and carries the position the page's shader gave it. | It runs the page's own shader on the page's own buffers, with nothing translated. |
| Pixel history tries a draw with each test off, inside the page's pass. | In a pass of the replay's own on the same attachments, between the page's draws, with occlusion queries and the scissor box shrunk to the pixel. Variants: every test off, a fragment stage that keeps everything (so a discard can be told from a miss), and one test on at a time. | A page's pass cannot be given an occlusion query set after it has begun, and the frame is already split there to read the pixel. |
| A multisampled target is resolved. | For draw_id, by taking one sample. | The average of two events' numbers is a third event's number. |
| Wireframe uses a polygon mode. | WebGPU has none. Each triangle draw is issued as a line list with the page's shaders, from an index buffer that names each triangle's three edges. | Lines are not culled, so a triangle that faces away still shows; the result says so. |
| Profile repeats each draw inside one timer query. | WebGPU times passes, not draws. Each draw is issued in two timed passes of the replay's own, 16 times in one and 32 in the other, and the figure is the difference: what a pass costs by itself cancels. An opaque draw is given a blend that replaces what is there, written in terms of the blend constant. | On a tile-based GPU (Apple's) only the last of several opaque draws to a pixel is shaded, so repeats of an opaque draw cost almost nothing: the fixture's full-screen shader read as 0.1 ms opaque and 1.7 ms blended. A blend that plainly replaces (one, zero) is taken for no blend; one that depends on the blend constant is not. With it the two read the same. |

Limits, all in `help limits`: targets of 8-bit or half-float RGBA for draw_id and overdraw; no overdraw through an sRGB view of the canvas; the mip view colours 8-bit 2D textures; uniform values for the first 48 members and four elements of an array; an `override` used as an array length is not worked out. On the stock profile the browser rounds GPU timestamps to 65.5 µs, so `profile` is good to about 4 µs a draw there; the deep profile has them fine.

**Found on the way, and fixed:** the WebGL `profile` repeated a draw inside one pass too, so the same full-screen shader read as 59 µs drawn opaque and 839 µs blended. It is now given the same blend for its repeats (the blend colour set to 1, source × colour + destination × (1 − colour)), and reads 867 µs. A target that cannot blend (integer or 32-bit float colour) is left as it was. `fixtures/slow/webgl2.html?opaque` and `webgpu.html?opaque` are the check, in `tests/findings.test.mjs` and `tests/webgpu.test.mjs`.

## Windows

Built and tested on 11 November 2026 on one PC: Windows 11 (x64), an NVIDIA GeForce RTX 3080 Ti, the installed Chrome 157, where WebGL is drawn through Direct3D 11 (ANGLE) and WebGPU through Direct3D 12 (Dawn). Until then nothing had been compiled anywhere but the Mac. The commands, their answers and the files are the same on both; what follows is what had to be different underneath.

| On macOS and Linux | On Windows | Why |
|---|---|---|
| The browser reads commands on descriptor 3 and writes replies on 4, set up between fork and exec. | It is given two pipe handles it inherits, and their values in `--remote-debugging-io-pipes`. Browsers are launched one at a time. | Windows has no numbered descriptors to hand over. A child inherits every handle marked inheritable when it starts, so two launches at once would each give their browser the other's pipe, and a pipe with a second holder does not close when its browser exits. |
| The control channel is a socket file, `control.sock`, in the home directory. | It is a named pipe, `\\.\pipe\scanline-<hash>`, where the hash is of the home directory's path, so each `SCANLINE_HOME` has its own. `runtime.json` records it as `pipe` where the others record `socket`. | A pipe is not a file. A client that finds every instance of the pipe in use for a moment waits and tries again, which is the pipe's form of a queue. |
| The socket is mode 600 in a directory set to mode 700. | The pipe is made with a security descriptor that names the user and nobody else, and refuses clients on other machines. The home directory is given a rule of its own (the user, the system and its administrators), not inherited from the folder above and passed on to every file in it. | A pipe's default security lets every user of the machine read it. File modes mean nothing on Windows; the default home (`%LOCALAPPDATA%\Scanline`) is private already, but one named by `SCANLINE_HOME` may not be, so the rule is set either way. The host does not start if it cannot set either. |
| The host is detached with `setsid`. | It is started with a console of its own that is never shown, and in its own process group. Before it is started, the command that starts it marks its own input and output as not to be inherited. | Closing the terminal must not stop the host, and no window must flash up for it or for the helpers it runs. Without the last step the host would hold the pipe the command writes its answer to, and whoever ran the command would wait for the host to exit. |
| The host stops on SIGINT and SIGTERM. | On Ctrl+C or Ctrl+Break in its console, on that console closing, on log-off and on shut-down. | What Windows has in their place. A process killed outright stops nothing on either. |
| The Debug key is held with Carbon's hot key API: F1 to F15. | With `RegisterHotKey`: F1 to F24. | Neither needs the person's permission, and both give a key to one application at a time. |
| `memory` quotes the GPU process's physical footprint, which includes the GPU allocations made for it. | It quotes the process's private bytes: the system memory it has committed. What it holds in a graphics card's own memory is not in that figure, and the sentence says so. | Windows has no one figure for both. A leak still shows as growth, in smaller numbers. |
| A local file's address is `file://` and its path. | The path is turned into an address: `C:\game\index.html` is `file:///C:/game/index.html`. | The system's full form of a Windows path (`\\?\C:\…`) is not an address a browser takes. |
| The pinned browser is unpacked with `ditto` (macOS) or `unzip`. | With the `tar` Windows ships with, named by its full path. | Windows has no `unzip`, and a `tar` from elsewhere on the `PATH` (Git's) does not read zip archives. |
| A release is a `.tar.gz` with `install.sh`. | A `.zip` with `install.ps1`. Nothing is signed. | What a Windows user expects. Signing needs a certificate. |

Two things were added to the command line because of Windows, and work everywhere:

- **JSON written with single quotes.** `cmd` does not treat single quotes as quotes, and Windows PowerShell drops the double quotes inside them, so `--filter '{"draws": [6, 8]}'` does not arrive whole in either. An object or a list may now be written `"{'draws': [6, 8]}"`, which every shell on every platform passes on unchanged. On Windows `--help` shows its examples that way.
- **Output is UTF-8 on both platforms**, and nothing was changed to make it so. A console shows it rightly, as does a pipe to a program that reads bytes. PowerShell decodes what it pipes or captures with the console's code page, so `« »`, `µ` and `→` arrive wrong there until the person sets `[Console]::OutputEncoding`. The README says how. For a shell that cannot be set (an agent's, often), `--ascii` on a command or `SCANLINE_ASCII=1` in the environment makes Scanline write ASCII only: `<<` and `>>` for the marks round page text, `x`, `us`, `->`, and a character of the page's as its code point. With `--json` each is a `\u` escape, so nothing is lost. It is asked for and not guessed: guessing would break the programs that read UTF-8 rightly.

What the PC showed that is about the GPU and not about Windows:

- **A value exactly between two is rounded the other way.** A tint of 0.5 is 127.5 and a grey of 0.1 is 25.5: Metal on the Mac gives 128 and 26, Direct3D on this GPU 127 and 25. One textured, tinted crate differs by one as well (131 for 132). The tests that read those pixels now take either value, in those channels only (`assertPixel` in `tests/host.mjs`); every other exact value in the suite is the same on both machines, and captures still replay identically, since a replay runs on the GPU that drew the frame.
- **WebGPU takes longer to start, and `launch` returned before the page was ready.** From asking for an adapter to having a device is about 0.7 s for a bare page through Direct3D 12 and over a second for three.js or PixiJS, against a fraction of that through Metal. `launch` waited for any context at all, a 2D canvas included, and PixiJS makes three of those at once; and an engine configures its WebGPU canvas only in its first frame, which a page started paused never reaches. So `launch(start: "paused")` then `step` ran frames the engine could not yet draw, and `capture` found no context. The probe now reports how far a page has got (an adapter asked for, requests in flight, devices made), and `launch` waits, for up to 4 s, for a WebGPU context or, on a paused page, for a device with nothing more in flight. A page that has asked for nothing is waited on for 1.2 s as before, and only a WebGL or WebGPU context ends the wait early.
- **GPU time is not steady on a desktop card.** The same frame of the slow scene read 0.27 ms, then 1 ms, then 2 ms and more, over a few seconds in which nothing changed: the card slows its clock when it has little to do. One reading before a change and one after therefore compares two states of the machine, and a frame made lighter can even read higher, because the card slows further. The slow-frame journey's test now takes three readings of each, turn about, and compares the middle ones (`turnAbout` in `tests/journeys.test.mjs`); its thresholds are unchanged. Where the readings of one unchanged frame are more than half as much again apart, the comparison is reported and not asserted, since it would say nothing about the shader: on the PC that was both journeys, WebGL and WebGPU, in the last run, so **the timing half of the slow-frame journey is in effect checked on the Mac only**. The rest of it (the pass and the shader found, the cost shown to be fill, the patch made and the picture compared) is asserted on both. In the same spirit `profile` on the PC puts the costly draw of bug b14 at some 20 µs, near enough to the fixed cost of a draw that changes target for the test to say what it means: each of the sparks after it is a small fraction of it. `help limits` says all this to an agent. `experiment` had the same weakness, measuring once without and once with. It now measures each three times, turn about, gives the middle reading of each, and says in capitals when the readings of one disagree by more than half as much again; its answer carries all six readings and a `steady` flag. The frames asked for are split over the three turns, of no fewer than ten frames each.
- **A pass can be shorter than a timestamp's step.** Outside the deep profile the browser rounds WebGPU timestamps to 65.5 µs. On this GPU a small pass begins and ends inside one step, and the probe took an equal pair for a pass that never ran, so `stats` counted only the rare pass that straddled a step and reported a mean of one whole step: about twenty times too high. An equal pair now counts as zero. This was wrong on the Mac as well, for any pass that cheap.
- **A WebGPU error could arrive after the step that caused it.** The browser checks a frame in its GPU process and reports back some milliseconds later. `step` answered as soon as the frames had run, so whether a validation error was in its answer or in the next command's was a race, which this machine lost once in three runs of the suite. `step` and `run_until` now wait for the WebGPU queue to finish what the frames submitted, for a quarter of a second at most, before they answer.
- **A texture the page had let go of was reported as gone.** A page that keeps a texture's view and drops the texture itself leaves the texture's handle for the collector. Once it was collected Scanline said the texture no longer existed, though the GPU holds it for as long as the view lives, and `patch_texture` refused it. The record of a view now keeps its texture's handle. The Mac's timing had hidden this; it is not about Windows at all.

What has not been checked on Windows is in `docs/BY-HAND.md` under "On Windows": everything that needs eyes, a real F9 press, the release and its installer, the pinned browser's real download, and a native debugger attached to the native-capture profile.

## Added, not in the specification

- **A capture says what is worth a look.** The specification puts lints in milestone 5. A first set came out of the evaluation and is built: draws that changed nothing, rejected calls and feedback loops, a viewport that is not its target's size, a clear clipped by a scissor box left on, a blended draw with opaque ones drawn over it, blending off on a translucent colour, a bound texture that cannot be sampled, and what the frame created and deleted. Each is worded as a fact about the frame, not a verdict.
- **What every event changed is measured when the capture is taken**, by reading its target back around each event in one more replay. `draw_list` shows it. A frame too large for that (more than about 600 million pixels read) goes without, and `draw` measures one event when asked.
- **A draw that changed nothing is replayed with each test off in turn**, so `draw` can say which test rejected it. This stands in for part of pixel history.
- **`draw` says where each uniform and each texture binding came from**: the call that set it, and whether that call was for this draw or an earlier one.
- **`resources` and `memory` flag leaks and churn** from the registry: many live objects created by one line over many frames, or far more objects created than are alive.
- **Call arguments in a capture's `commands` table are stored for reading**: handles for objects, `prg_1.name` for uniform locations, WebGL's names for the enumerated arguments of the common methods.
- **A command waits for the events the browser sent before its reply.** Replies and events are handled by different tasks, so `step` could otherwise report no errors for a frame that raised one.

- **A page that draws from timers alone still steps.** A frame is "the clock moves, the frame callbacks run, then the timers that have come due run", so a loop on `setTimeout` pauses and steps like any other.
- **Errors carry the frame they were thrown in.** The browser reports an uncaught error after the probe's end-of-frame work, by which time the frame number has moved on. The probe notes the throw as it passes.
- **Frames are numbered from 1**, and everything that happens during a frame carries the number of the image it produces.
- **A command with no reply times out with its name** (30 s), after spike S4 met one.
- **`status` reports the browser's and the GPU process's process IDs**, which telemetry will need and the crash tests use.
- **Object handles are the probe's own numbers** (`tex_17`), with a suffix for objects in a worker or another frame (`tex_17_w2`). The host remembers which page load each handle it has shown came from, so a handle from before a reload is refused with a message, as the specification asks.
- **`resource` takes a context handle** and returns the WebGL state a draw would use now, from the mirror. `verify: true` checks the mirror against the context.
- **Texture rows are shown the way they were rendered.** A WebGL render target's first row is its bottom, so it is flipped for display and for `pixels`; `flip: false` gives storage order.
- **The probe's records ride on the page's objects as private class fields**, one generated class per kind of object. A shared lookup saw every type of object and cost about 75 ns a call; one class per kind costs about 17.
- **A page's own timer queries win.** Only one can be active, so when the page begins one, Scanline ends its own and stops timing that context.

## Known gaps in what is built

- Unlabelled WebGPU objects are not given generated labels, which the specification lists as a modification. They are named by handle in results instead.
- "Last used" is exact for WebGL objects (at bind, and once a frame for what is bound when drawing). For WebGPU it is sampled: on a frame in sixteen, on any frame that begins a quarter of a second or more after the last sampled one (so frames stepped by hand are each looked at), and for the rest of any frame in which the page makes an object (so one made and used within a frame is seen), the probe notes the pipelines, bind groups, vertex and index buffers and bundles a pass sets, and the textures it draws to. Textures, buffers and samplers held by a used bind group or bundle are marked when the inventory is read. Rows say `used ~f120` or `not seen in use`. Following every frame would put a lookup on every `setBindGroup`.
- WebGPU pass timing measures one frame at a time: a frame that ends while the previous readback is in flight goes unmeasured (about one frame in three at 60 Hz here).
- Timer queries and timestamp writes are only added at the `observe` level and above, and never in unmodified mode.
- If a WebGL 2 page has set the default framebuffer's read buffer to `NONE`, the readback raises a GL error the page can see.
- Step broadcasts to every probe at once (frames and workers) but does not keep them in step with each other frame by frame.
- Console lines are tied to frames by wall-clock time against the top frame's record, so a line logged within a millisecond of a frame boundary can be one frame out. Errors are exact.
- `document.timeline` and event time stamps do not read the virtual clock yet.
- Media elements are not paused with the clock; audio contexts are.
